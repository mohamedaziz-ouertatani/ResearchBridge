# Potential Applications Evidence Grounding — Design

## Problem

`assess_applications()` currently surfaces application claims that are too weak to be credible. Two real production examples:

1. `"In this paper will deliberate various techniques of data mining which are useful for predicting performance level of students."`
2. `"These are aided by the automation of many procedures involved in typical student activities, which manage huge amounts of information collected through software applications for technology-oriented learning."`

Neither is a genuine external application. (1) restates the paper's own predictive task under the guise of "useful for X." (2) is a homonym collision — "applications" meaning software/computer programs, not "applications of this research."

Real benchmark data (`benchmark/extraction_eval_results.json`, generated by `rb-extract-evaluate` against the 40-paper Sec 25 ground truth) confirms this isn't anecdotal: the `applications` field has the lowest precision of any validated extraction field for the hybrid extractor actually used in production — **precision 0.417, recall 0.303** (measured on raw extractor output, before `validate_claim_type` runs).

## Current pipeline (as traced)

```
extraction/heuristic.py::HeuristicExtractor   — cue phrases incl. "useful for" (medium confidence)
extraction/semantic.py::SemanticExtractor     — per-sentence similarity to anchor
                                                 "A real-world application this work supports."
extraction/hybrid.py::HybridExtractor         — medium-confidence heuristic hit always wins
extraction/pipeline.py::_process_paper()      — grounding check, then validate_claim_type()
extraction/validation.py::validate_claim_type — "applications" branch: _has_application_signal()
                                                 (regex only, always returns tier=None)
assessment/applications.py::assess_applications — SELECTs claim_type=="applications" for papers
                                                   within RELEVANCE_DISTANCE; returns verbatim,
                                                   one ApplicationRecord per claim, no filtering
                                                   beyond claim_type + paper-level distance
assessment/build.py                           — assembles potential_applications JSON
api/schemas.py / AssessmentReport.tsx         — renders {application, source_paper, paper_id}
```

Root cause, traced to exact regex lines in `extraction/validation.py`:

- Example 1: `_VAGUE_USEFULNESS_RE` only blocks a short catch-all list (`"future studies/work/research/general purposes"`); `_APPLICATION_LANGUAGE_RE`'s `\b...useful (to|for|in) [a-z]` clause accepts any following word, including a bare restatement of the paper's own task.
- Example 2: `_APPLICATION_LANGUAGE_RE`'s `\bapplications? (such as|include|in|to|for)\b` matches the literal substring "applications for" regardless of whether "application(s)" means "use-case" or "software program."

## What stays unchanged (confirmed in review, do not touch)

- Fully extractive/deterministic pipeline — no LLM, no synthesis, anywhere.
- Verbatim grounding (`_quote_is_grounded`) and real `evidence_id` provenance.
- Independent per-paper provenance — multiple papers stating the same application remain separate `ApplicationRecord`s, never merged (already correct).
- `None` (no relevant papers retrieved) vs. `[]` (relevant papers, no admissible application) semantics — already correct, shipped in the dimension-coverage work.
- `heuristic.py`'s cue-phrase list — non-authoritative candidate proposal; fixing the bug there in addition to the validator would duplicate the fix in two places for no benefit, since `validate_claim_type` is the single downstream point of truth for both extractors' output.
- `coverage.py` / `DimensionCoverage` — untouched by this design.
- No cross-paper application clustering or synthesis (`opportunities.py`'s existing, deliberate boundary).

## Architectural options considered

| | A: field-specific validation + same-paper overlap | B: full gap `ClaimRole` adaptation | C: shared `ClaimRole`/`EvidenceRole` framework |
|---|---|---|---|
| Fixes both reported cases | Yes | Yes (no better than A) | Yes (no better than A) |
| New schema | None (`validation_tier` already exists, unused for applications) | None, but a role field would eventually be wanted | Likely a shared role table/enum |
| Complexity | Low | Medium-high (new 3-way taxonomy with no confirmed consumer) | Very high (generalizing from n=2 real instances) |
| Overengineering risk | Low | High | Very high |

**Decision: Option A.** `research_gap`'s `classify_claim()` role system is real prior art, but its *content* (self-resolution language, field-scope language, cross-paper addressing) is gap-specific and doesn't transfer. What transfers is one column (`validation_tier`, already unused for applications) and one technique (own-contribution-overlap — comparing a claim to the *same paper's* other claims), not the taxonomy or the cross-paper machinery. A shared abstraction is premature at two concrete instances with materially different rule content.

**Architectural question answered:** `claim_type` is not the wrong dimension. What was missing is exactly what `research_gap` already has and `applications` doesn't — a within-type strength signal (the existing, currently-unused `validation_tier` column) plus a cross-claim consistency check — not a new second semantic dimension in the schema.

## The own-task-overlap edge case (resolved)

A genuine application is often semantically close to the paper's own task (that's what makes it credible) — so "high similarity → reject" is wrong and would reject genuine cases like: task *"predict student academic performance"* → application *"support universities in identifying students at risk of failure early enough for intervention."*

**What the overlap check is actually for:** not "is this related to the task" (expected, fine) but "is this sentence a near-total paraphrase of the task with nothing added" — no actor, no setting, no downstream action beyond the task itself.

**Two-gate design**, because embedding similarity cannot make this distinction alone (it's dominated by shared domain vocabulary regardless of which case it is) — the primary discriminator has to be lexical/structural:

```
Gate 1 — extraction/validation.py::validate_claim_type, "applications" branch
  (per-candidate, no paper context; runs at extraction time)

  Reject unless the sentence:
    (a) contains a genuine deployment-framing verb/construction (existing
        _APPLICATION_LANGUAGE_RE family, tightened), AND
    (b) that construction's object/complement names an actor/institution/
        setting term (university, hospital, bank, clinician, instructor,
        policymaker, industry, "compliance team", "decision-makers", or a
        deployment-setting phrase like "in clinical practice"/"at scale")
        OR a downstream-action term distinct from the paper's own
        predictive/detection/classification verb (intervention, triage,
        manual review, counseling, resource allocation, policy,
        remediation, prioritization), AND
    (c) is not reducible to the bare "software/mobile/web/desktop/computer/
        online application(s)" noun phrase with nothing else qualifying it
        (homonym exclusion — masks that phrase before matching (a)/(b)).

  Sets validation_tier="strong" on acceptance. No "weak" tier — hedged/
  generic language (item E) is rejected outright, per explicit decision.
  Rejects hedged modal language ("could potentially be useful") with no
  named concrete context, same as today's _VAGUE_USEFULNESS_RE but folded
  into the same structural requirement rather than a separate blocklist.

Gate 2 — assessment/applications.py (per-claim, same-paper context; runs at
  assessment time, only for claims that already passed Gate 1)

  Reject if this claim's cosine similarity to the paper's own best-
  matching problem/method/main_contribution/results claim (already present
  in build.py's papers_with_claims bundle — no new query) exceeds a HIGH
  threshold — provisionally 0.92, NOT gap's 0.85 (that number was
  calibrated for a different comparison against a dataset that doesn't
  exist for applications; 0.92 is a reasoned starting point because Gate
  2's job has narrowed to "near-total paraphrase only," not general
  overlap, given Gate 1 already does the primary discrimination) — flagged
  explicitly as provisional pending a live-corpus spot-check (same
  technique as the DIMENSION_MATCH_SIMILARITY calibration), not shipped as
  a trusted final number.
```

Gate 2 exists specifically because Gate 1's keyword-presence matching cannot perfectly enforce "the actor must be the deployment verb's object, not a bare adjective" without a real parser (e.g. "university-level performance prediction" contains "university" but as a modifier, not an object — it slips past Gate 1 and needs Gate 2's high-overlap backstop to catch it as a near-total paraphrase). Six worked examples, spanning both directions and this specific residual case, are recorded in the conversation and become the regression tests below.

**Expected failure mode (accepted tradeoff, matching "ok to return few or zero"):** false negatives — a genuine application described without any curated actor/action vocabulary and not close enough to trip Gate 2 either lands in an ambiguous zone this rule rejects. A smaller residual false-positive risk remains (an actor word used loosely without genuinely describing external use, that also doesn't trip Gate 2) — narrowed by the two-gate design relative to today, not eliminated.

## Necessary changes, by layer

| Layer | Change | 
|---|---|
| `extraction/heuristic.py`, `extraction/semantic.py`, `extraction/hybrid.py` | None |
| `extraction/validation.py` | Rewrite the `applications` branch: Gate 1 above, sets `tier="strong"` |
| `db/models.py` | None — `validation_tier` already exists |
| `extraction/pipeline.py` | None — already persists whatever `validate_claim_type` returns |
| `assessment/applications.py` | Add Gate 2 (own-task-overlap, ported technique from `gaps/detect.py::_own_contribution_overlaps`, cited not duplicated silently); change `assess_applications` signature to take the already-assembled `papers_with_claims` bundle + `embedder` instead of `session` + a redundant DB query — becomes a pure function, dropping its DB dependency entirely, consistent with `novelty.py`/`coverage.py` |
| `assessment/build.py` | Update the one call site to match the new signature |
| `api/schemas.py`, `frontend/components/AssessmentReport.tsx` | **Not required.** Deferred — optional future exposure of `validation_tier` for UI transparency, no correctness dependency |

No database migration.

## Test plan

**`tests/test_extraction_validation.py`** (Gate 1, lexical only):
1. `"...useful for predicting performance level of students."` → reject
2. `"...software applications for technology-oriented learning."` → reject
3. `"deployed by banks to flag suspicious transactions for manual review by compliance teams."` → accept — the case that proves overlap-alone would have been wrong
4. `"can be used by dermatologists to prioritize which patients need urgent biopsy."` → accept
5. `"we develop a system for predicting student outcomes."` → reject
6. `"these findings could be useful for future studies in general."` → reject
7. `"can be applied to accelerate drug discovery pipelines in pharmaceutical R&D."` → accept

**`tests/test_assessment_applications.py`** (Gate 2, needs a fake embedder + same-paper claims):
8. Gate 2 accepts a genuine application even at high sentence-level similarity to the task claim — does not re-reject what Gate 1 already correctly accepted
9. Gate 2 rejects a near-total-paraphrase application that slipped past Gate 1 ("university-level performance prediction" case)
10. Multiple genuine applications from different papers preserved independently (re-verify under new signature)
11. Relevant papers, no admissible application → `[]` (re-verify)
12. No relevant papers → `None` (re-verify)

**Benchmark re-run** (`rb-extract-evaluate`), before/after comparison, committed alongside the code change:
- `evaluate()` — hybrid extractor's applications precision/recall vs. the 0.417/0.303 baseline
- `evaluate_claim_type_validation()` — own-field-acceptance-rate (must not collapse — a stricter regex rejecting genuinely-good ground-truth text is a false-negative regression) and cross-field-rejection-rate (must not regress) for the `applications` field specifically

Explicit caveat: the benchmark's ground-truth `applications` field contains only already-correctly-labeled text, so it cannot itself catch the two reported false positives — it's a guardrail against over-correction (recall collapse), not the primary evidence source. The unit tests above are the primary regression coverage.

**Live-corpus spot-check** (new task, same technique as the dimension-coverage Task 12 calibration): run the real embedder against a handful of real corpus papers to sanity-check the 0.92 Gate 2 threshold before treating it as trusted; adjust and document if the real similarity distribution doesn't support it.

## Out of scope

- `schemas.py` / `AssessmentReport.tsx` exposure of `validation_tier` (nice-to-have, deferred)
- Idea-specific claim-level relevance (comparing an application claim to the *specific input idea*, not just paper-level `RELEVANCE_DISTANCE`) — a real, separately-scoped gap, not required by the mandatory regression list
- A `tier="weak"` accepted-but-flagged tier — explicitly rejected; hedged language is rejected outright
- Any shared `ClaimRole`/`EvidenceRole` framework (Option C)
- New calibration infrastructure (a `gap_calibration_groups.yaml`-equivalent for applications) — existing benchmark + unit tests are sufficient for this scope
- `heuristic.py`'s cue-phrase list
- Any change to `coverage.py` / `DimensionCoverage`
- Cross-paper application clustering or synthesis
